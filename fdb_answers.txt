Q1: Decouple the components because it allows each component to be scaled separately and allow recovery logs separate from storage. TMS handles coordinating transactions, resolving conflicts, and some logging. SS handles storing the actual data and applying the commits to the data.
Q2: The Resolver of the TMS handles detecting read-write conflicts between concurrent transactions and it happens during the commit phase. If the read version is older than the write version, the transaction is aborted and the client must retry.
Q3: Read version allows the sequencer to enforce clean, repeatable reads without locks by indicating the exact point in time the read requests. It also allows snapshots to guarantee consistent reads of that specific version.
Q4: Standard reads are checked with resolver to ensure that there are no read-write conflicts. Snapshot reads request an exact historical version and thus do not need to be checked against later write conflicts, so the resolve does not check them and the transaction cannot abort. The primary trade-off is either up-to-date reads vs. no-conflict historical reads.
Q5: FDB recovery is cheaper because the log and storage servers are separate, so spinning up a crashed storage server simply means fetching the mutation list from the logs. Essentially, since the service is decoupled, crashes affecting the data storage do not affect the logs required to reconstruct the storage quickly so recovery is cheap.
